# 原理与实测

本文记录这个模块背后的调研和实验数据，包括走过的弯路。

测试设备：小米平板 5 Pro，HyperOS，Magisk 30.6，PD 充电器（65W）。

---

## 一、先看官方做了什么

### 1.2 平板上的实际情况

```
persist.vendor.smartchg = （空）
smart_chg 节点：qcom-battery 和 power_supply/battery 下都不存在
night_charging 节点：存在
```

按官方代码的能力位判断，`(0 & 2) == 0` → 导航断充能力位为 0。
**小米自己的代码就判定这台设备不支持导航断充。**

HAL 服务在跑（`init.svc.micharge-hal-1-0=running`），代码也编译进去了，
但底层驱动没暴露节点，能力位也没置位，所以那套逻辑是死的。

### 1.3 HAL 能写什么

从 `vendor.xiaomi.hardware.micharge@1.0-impl.so` 整理的完整可写路径清单：

```
battery/charge_control_limit      ← PD 电压档位
battery/input_suspend             ← 断输入（0/1）
battery/night_charging            ← 限充开关（0/1）
battery/smart_batt
qcom-battery/input_suspend
qcom-battery/night_charging
qcom-battery/cool_mode
qcom-battery/power_max
main/cool_mode
```

HAL 方法只有：`setMiChargePath` / `setNightChargingState` / `setInputSuspendState` /
`setCoolModeState` / `setWlsTxSpeed` / `setRxCr` / `setBtState` /
`setSmCountReset` / `setUpdateWirelessFw`。

**没有 `setCurrent`，也没有 `constant_charge_current(_max)`。**

结论：官方能力上限就是"到 80% 断充"，做不到任意电流限流。

## 二、走过的弯路：charge_control_limit

`battery/charge_control_limit` 是 HAL 里唯一看起来像"限流"的节点，0~16 档。
PD 快充下逐档实测：

| CL 值 | 电池电流 | PD 电压 |
|---|---|---|
| 0 | -4.19 A | 8.40 V |
| 9 | -4.19 A | 8.41 V |
| 10 | -4.03 A | 8.39 V |
| 11 | -3.41 A | 8.25 V |
| **12** | **-1.27 A** | **4.76 V** |
| 13 | -2.09 A | 8.60 V |
| 14 | -1.31 A | 6.13 V |
| 15 | -2.10 A | 8.66 V |
| 16 | -3.34 A | 5.97 V |

**非线性、不单调、来回跳。** 它实际是"选 PD 电压档位"，写下去触发一次重新协商，
电压在 4.7~8.7V 之间跳，电流跟着乱变。12 档最低，16 档反而回升。

**所以这条路做不了伪旁路**——没有平滑、单调、可微调的执行器。

## 三、真正的控制节点：constant_charge_current_max

### 3.1 怎么找到的

在 Scene 里调"充电调速"时，UI 上有行小字"实际上限电流：50mA"，
但 `battery/constant_charge_current` 读出来是 0。顺藤摸瓜：

```
battery/constant_charge_current_max = 50000    ← UI 那行小字
bms/constant_charge_current_max     = 50000    ← 同步
battery/constant_charge_current     = 0        ← 驱动按上限算出的结果
```

**Scene 写的是 `constant_charge_current_max`（上限），不是 `constant_charge_current`（实际值）。**
实际电流是驱动根据上限算出来的，上限太小就直接归零。

节点权限是 `-r--r--r--`，但 `chmod 666` 之后 root **可以直接写**（rc=0 生效）。

### 3.2 完整扫描

写 `constant_charge_current_max`，每档等 4 秒读取（电量 90~92%，PD 充电器）：

| CM 设定 | 电池净电流 | 输入 | 电压 | 状态 |
|---|---|---|---|---|
| 2000 mA | -4.51 A | 1.59 A | 8.7 V | 限流没生效，仍是快充 |
| 1200 mA | -4.64 A | 1.37 A | 8.7 V | 同上 |
| 800 mA | -4.67 A | 1.37 A | 8.8 V | 同上 |
| 600 mA | -4.68 A | 1.69 A | 8.8 V | 同上 |
| **500 mA** | **+242 mA** | 32 mA | 8.3 V | 滑入断充 |
| **400 mA** | **+270 mA** | 32 mA | 5.2 V | 滑入断充 |
| 300 mA | -268 mA | 491 mA | 5.08 V | 正常限流 |
| 250 mA | -216 mA | 511 mA | 5.09 V | 正常限流 |
| 200 mA | -162 mA | 506 mA | 5.05 V | 正常限流 |
| 150 mA | -114 mA | 356 mA | 5.08 V | 正常限流 |
| 120 mA | -67 mA | 386 mA | 5.09 V | 接近零点 |
| 100 mA | -63 mA | 343 mA | 5.11 V | 接近零点 |
| **80 mA** | **+15 mA** | 242 mA | 5.12 V | **悬浮** |
| **60 mA** | **+15 mA** | 280 mA | 5.10 V | **悬浮** |
| **50 mA** | **+13 mA** | 272 mA | 5.10 V | **悬浮** |
| 40 mA | +318 mA | 0 | 5.19 V | 滑入断充 |
| 30 mA | +310 mA | 0.6 mA | 5.16 V | 滑入断充 |
| 20 mA | +312 mA | 0 | 5.17 V | 滑入断充 |

三个发现：

1. **CM ≥ 600mA 时无效**，PD 保持 8.7V 高压快充，限流被忽略
2. **CM = 500/400mA 时反而断充**（PD 掉到 5V，输入只剩 32mA）
3. **CM = 50~80mA 是甜点**，电池净电流 +13~15mA，几乎为零

### 3.3 稳定性验证

CM = 60mA，连续 30 秒采样：

```
cur = +15, +17, +17, +17, +17, +15, +15, +13, +13, +13 mA
in  = 390, 238, 305, 323, 248, 310, 256, 279, 345, 270 mA
vol = 5.09 ~ 5.12 V
cap = 91%（无变化）
```

波动 ±2mA，电量不动。再持续观察 5~6 分钟，**CM 没有被系统重置**
（该节点不属于 HAL 管理范围，没有服务周期性回写它）。

## 四、官方"随电量降速"是怎么做的

内核日志里能看到 `QCOM-STEPCHG`：

```
handle_step_chg_config: OCV = 4362000  Step-FCC = 10800000uA
handle_step_chg_config: OCV = 4192000  Step-FCC = 1000000uA
handle_jeita: BATT_TEMP = 279  FCC = 12400000uA  warm=480 cool=150
```

驱动读 **OCV（开路电压）** 查表降流，与电量百分比无关（电量涨→电压涨→自动降档）。

### device tree 里的原始配置

从 `/sys/firmware/devicetree/base/vendor/qcom,battery-data/.../` 读出来的：

`qcom,step-chg-ranges`（单芯值，本机双芯并联所以翻倍）：

| 电压区间 | 单芯电流 |
|---|---|
| 3.60 ~ 3.80V | 5.4 A |
| 3.80 ~ 4.30V | 3.6 A |
| 4.30 ~ 4.35V | 2.5 A |

其他精确参数：

| 参数 | 值 | 含义 |
|---|---|---|
| `qcom,fg-cc-cv-threshold-mv` | 4340 mV | CC→CV 切换阈值 |
| `qcom,max-voltage-uv` | 4350000 µV | 恒压目标 |
| `bms/termination_current` | 400 mA | 充满判定电流 |
| `qcom,fastchg-current-ma` | 6250 mA | 单芯快充上限（×2 = 12.5A） |
| `mi,step-charge-high-vol-curr-max` | 6720 mA | 小米加的高压段限流 |

### 涓流阶段没有主动控制

`taper-fcc` 在 dmesg 里**恒为 0**，dtb 的 `step-chg-ranges` 也只到 4.35V 就结束，
**没有 taper 段配置**。

所以末期的真实过程是纯被动的：

```
4.30~4.35V  阶梯表给 2.5A（精确）
     ↓
4.34V       切 CV（精确阈值）
     ↓
CV 阶段     I = (4.35V - Vbat) / 内阻 → 电流自然衰减（被动，无控制）
     ↓
< 400mA     判定充满，停充（精确阈值）
```

没有"按 mA 精确控制涓流"的机制，软件只设两个阈值。

### 与伪旁路的关系

两者是"上限取最小值"：

```
实际充电电流 = min( 阶梯表给的 FCC, 我们写的 CM, CV 阶段允许的电流 )
```

所以写 `CM=60mA` 时，即使驱动允许 10.8A，最终也只有 60mA。

## 五、踩过的坑

| 现象 | 原因 | 处理 |
|---|---|---|
| 反复改电流后 PD 掉到 5V、输入 0 | PD 协商被反复打断 | **物理拔插充电器**才能恢复 |
| `constant_charge_current` 写入 rc=1 | 它不是主控制点 | 写 `constant_charge_current_max` |
| CM 设 100mA 时 CC 变 0 | 上限太小，驱动放弃充电 | 下限设 50mA 以上 |
| 电量 >90% 后低电流设置全被归零 | 进入 CV 阶段，系统强势接管 | 属正常，高电量时效果有限 |
| WebView 改了页面没变化 | 缓存 | `am force-stop` + 删 `app_webview` |

## 六、和真旁路的差距

K70 有官方旁路位 `smart_chg`（`persist.vendor.smartchg` = 6，bit1/bit4 置位），
写 `0x{阈值<<16|3}` 就是驱动级真旁路，电池电流精确 0，且拔插不丢。

平板没有这个位，只能做伪旁路：靠一个电流上限节点把净电流压到噪声级（±15mA）。

差异：

| | 真旁路 | 伪旁路 |
|---|---|---|
| 电池电流 | 精确 0 | +13~17mA |
| 维持方式 | 驱动保持 | 模块周期调整 |
| 拔插充电器 | 状态保留 | 重新初始化 |
| 依赖 | 厂商节点 | 任意有电流上限的机器 |

对电池的实际影响很接近——+15mA 已经是测量噪声级别，电池基本不参与充放电。
